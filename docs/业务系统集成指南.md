# 业务系统集成指南

本文档面向**业务项目中的开发工程师**或负责改代码的 **AI 助手**，说明如何在真实业务系统里安装、配置并使用 [base-agents](https://github.com/AICodeFactory/base-agents)（Python 包分发名：`role-aware-business-agent`，导入包名：`business_agent`）。

阅读完本文档后，你应能独立完成：依赖安装、角色与权限建模、业务工具注册、`BusinessAgent` 接入与任务结果落库。

---

## 1. 包在业务架构中的位置

本库提供的是**可嵌入的 Agent 编排层**，不负责：

- 用户登录、会话、JWT 签发；
- 业务数据库 schema 与 ORM；
- 大模型 API Key 的账号体系（仅使用你传入的 `model` 或自定义运行时）。

业务系统需要负责：

- 从网关 / 会话中解析出当前用户身份，构造 `RoleContext`；
- 注册与业务域相关的工具（内部 Service、HTTP 客户端、ORM 查询等）；
- 将 `TaskResult` / `TaskEvent` 写入你们的任务表、日志或消息队列；
- 配置 LangChain / 模型供应商的环境变量或凭证（若使用默认的 `DeepAgentsRuntime`）。

## 2. 环境与安装

### 2.1 版本要求

- **Python**：`>= 3.10`（以仓库内 `pyproject.toml` 为准）。
- **Git**：从 GitHub 安装时需要。

### 2.2 安装方式

**从 GitHub 固定版本（推荐给生产依赖声明）：**

```bash
pip install "git+https://github.com/AICodeFactory/base-agents.git@main"
# 或锁定 tag / commit：
pip install "git+https://github.com/AICodeFactory/base-agents.git@v1.0.0"
```

**在业务仓库的 `requirements.txt` 中**可直接写上述一行，便于 CI 与部署一致。

**从 PyPI 安装**（若维护者已发布）：

```bash
pip install role-aware-business-agent
```

### 2.3 传递依赖与模型调用

安装本包会拉取 `deepagents`、`langchain`、`langchain-core`、`langgraph` 等。使用默认运行时 `DeepAgentsRuntime` 时，需要在运行环境中配置**模型供应商**所要求的 API Key、Base URL 等（具体变量名以你们选用的模型与 LangChain 集成方式为准）。未配置时，首次真正调用模型会失败，表现为 `TaskResult.status == failed` 且 `error` 为异常信息。

## 3. 核心对象一览

| 对象 | 作用 |
|------|------|
| `RoleContext` | 单次请求的业务身份：角色、用户、租户、权限集合、扩展属性。 |
| `AgentRequest` | 一次调用：用户输入 `input`、必填 `role`、可选 `task_id` / `metadata`。 |
| `ToolRegistry` | 注册多个业务工具；运行前按角色过滤可见工具。 |
| `BusinessTool` / `@business_tool` | 描述工具元数据、允许角色、所需权限及实际执行函数。 |
| `BusinessAgent` | 组装注册表与运行时，暴露 `async def ainvoke(request) -> TaskResult`。 |
| `DeepAgentsRuntime` | 默认实现：将可见工具转为 LangChain `StructuredTool` 并调用 DeepAgents。 |
| `AgentRuntime`（协议） | 可替换为自定义实现，便于单测或不连真实模型。 |
| `TaskResult` | 返回给调用方：任务 ID、状态、输出、错误、步骤、元数据等。 |
| `TaskEvent` | 完成时回调中的事件，内含完整 `TaskResult`。 |

公开导出见包内 `business_agent/__init__.py`。

---

## 4. 推荐集成步骤

1. **定义角色枚举或常量**（与你们 IAM / 岗位体系对齐），例如 `sales_manager`、`customer_service`。
2. **在 HTTP 中间件或 Service 层**从 Token / Session 解析 `user_id`、`tenant_id`、`permissions`，构造 `RoleContext`。
3. **实现业务工具函数**：使用 `@business_tool` 声明 `allowed_roles`、`required_permissions`；需要时在函数签名中加入 `role_context: RoleContext`（未在模型参数里出现时，运行时会自动注入）。
4. **集中注册工具**：`ToolRegistry([tool_a, tool_b, ...])` 或逐个 `register`。
5. **构造单例或请求级 `BusinessAgent`**：传入 `model`、`tool_registry`、可选 `on_complete`。
6. **在异步路径中** `result = await agent.ainvoke(AgentRequest(...))`。
7. **根据 `result.status` 分支**：成功读 `result.output`；失败读 `result.error`；需要审计时读 `result.to_dict()` 或持久化 `TaskEvent`。

仓库内完整可运行示例：`examples/basic_usage.py`。

## 5. 角色与权限：`RoleContext`

### 5.1 字段说明

- `role`（必填）：业务角色字符串，与工具上的 `allowed_roles` 对应。
- `user_id`、`tenant_id`（可选）：用于审计、多租户隔离、下游 API 头。
- `permissions`：细粒度权限名集合；工具可声明 `required_permissions`，调用方角色**必须包含**全部声明权限工具才可见。
- `attributes`：任意扩展键值（部门、区域、数据范围等），`to_dict()` 会带出，便于日志与下游传递。

### 5.2 可见性规则（Agent 层）

对某个工具：

- **`allowed_roles` 为空**：不限制角色（任意 `role` 可见）。
- **非空**：当前 `role` 在列表中，或列表含通配符 `"*"`，则通过角色检查。
- **`required_permissions` 为空**：不额外要求权限。
- **非空**：当前 `RoleContext.permissions` 必须**包含其中全部**权限名。

两层条件**同时满足**时，工具才会进入本次请求的可见列表，并交给运行时（模型只能在该集合里选工具）。

### 5.3 与业务鉴权的关系

Agent 层只做「工具是否暴露给模型」的前置过滤。**业务系统仍须在工具内部**根据 `role_context` 做最终鉴权（能否查该客户、能否改单等），并打审计日志。不要把 Agent 层当作唯一安全边界。

## 6. 工具开发约定

### 6.1 装饰器注册

```python
from business_agent import RoleContext, business_tool

@business_tool(
    name="query_orders",
    description="查询客户订单",
    allowed_roles=["sales_manager", "customer_service"],
    required_permissions=["order:read"],
)
async def query_orders(customer_id: str, role_context: RoleContext) -> dict:
    # 在此调用你们自己的 Service / DAO，并做最终权限校验
    ...
```

- `name` / `description` 可省略，默认用函数名与 docstring。
- 同步函数也可注册；内部会通过线程池等方式适配异步调用链。

### 6.2 `role_context` 注入规则

若函数签名包含名为 `role_context` 的参数，且模型未传入该参数，运行时会**自动注入**当前请求的 `RoleContext`。若你们自行封装 LangChain 工具，需保证最终仍调用 `BusinessTool.ainvoke(role_context, **kwargs)` 这一路径，以免丢失上下文。

### 6.3 显式拒绝

若某次调用绕过了可见性（例如自定义代码直接调工具），`BusinessTool.ainvoke` 会在校验失败时抛出 `ToolAccessError`（`PermissionError` 子类）。

## 7. 发起请求：`AgentRequest`

```python
AgentRequest(
    input="用户自然语言任务描述",
    role=RoleContext(...),
    task_id="可选，不传则自动生成 UUID",
    metadata={"trace_id": "...", "channel": "web"},  # 会与运行结果元数据合并
)
```

- `metadata` 会合并进 `TaskResult.metadata`，便于链路追踪；失败时也会带上 `error_type`、`visible_tools` 等。

---

## 8. `BusinessAgent` 构造参数要点

| 参数 | 说明 |
|------|------|
| `model` | 传给默认 `DeepAgentsRuntime` 的模型标识或 LangChain 模型对象（与 DeepAgents / LangChain 版本一致）。 |
| `tool_registry` | 工具注册表；可与 `tools=` 二选一或组合（内部会归一为注册表）。 |
| `runtime` | 替换为自定义 `AgentRuntime`（例如单测 Fake、自研编排）。 |
| `runtime_kwargs` | 传给 `DeepAgentsRuntime` 的额外关键字，如 `instructions`、`agent_kwargs`。 |
| `on_complete` | 单个或列表；任务到达**终态**（成功、失败、取消）后调用，参数为 `TaskEvent`。 |
| `raise_callback_errors` | 默认 `False`：回调异常记入 `result.metadata["callback_failures"]`；设为 `True` 时在回调失败时抛出 `CallbackError`。 |

## 9. 任务结果与回调

### 9.1 `TaskResult`（`ainvoke` 返回值）

- `status`：`TaskStatus` 枚举；当前实现中常见终态为 `succeeded`、`failed`、`cancelled`。
- `succeeded`：便捷布尔属性。
- `output` / `error`：成功时的模型侧输出；失败时的异常字符串。
- `steps`：工具调用步骤列表（类型为 `ToolCallRecord`）；**默认 `DeepAgentsRuntime` 可能未填充步骤**，若你们强依赖逐步审计，可自定义 `AgentRuntime` 在 `RuntimeResult.steps` 中写入，或关注后续版本实现。
- `to_dict()`：便于序列化入库或写日志。

### 9.2 `on_complete` 回调

用于「任务已结束」时异步写库、发 MQ、通知前端。回调可以是同步或异步函数；多个回调会依次执行，失败默认不中断主流程（除非 `raise_callback_errors=True`）。

### 9.3 业务侧持久化建议

至少保存：`task_id`、`status`、`role`（或 `role.to_dict()`）、`input`、终态时间、`error`、`output` 摘要。需要合规时保留 `metadata` 与 `steps`。

## 10. 在 Web 服务中调用（示意）

以下仅为结构示意，非完整生产代码。

```python
from fastapi import FastAPI, Depends

from business_agent import AgentRequest, BusinessAgent, RoleContext, TaskEvent, ToolRegistry

app = FastAPI()

# 伪依赖：从请求解析当前用户
def get_role_context() -> RoleContext:
    return RoleContext(
        role="sales_manager",
        user_id="u_123",
        tenant_id="t_001",
        permissions=["order:read"],
    )

tool_registry = ToolRegistry()  # 在启动时 register 你们的工具

@app.on_event("startup")
async def startup() -> None:
    app.state.agent = BusinessAgent(
        model="gpt-4.1",
        tool_registry=tool_registry,
        on_complete=[persist_task_event],  # 你们实现的异步写库
    )

@app.post("/agent/run")
async def run_agent(
    payload: dict,
    role: RoleContext = Depends(get_role_context),
):
    agent: BusinessAgent = app.state.agent
    result = await agent.ainvoke(
        AgentRequest(input=payload["input"], role=role, metadata=payload.get("metadata") or {})
    )
    return result.to_dict()
```

要点：**接口层必须异步**使用 `ainvoke`；不要将 `RoleContext` 设为全局可变状态，应每请求新建。

## 11. 测试与自定义运行时

单测或流水线中可不连真实大模型，实现 `AgentRuntime` 协议：

```python
from collections.abc import Sequence

from business_agent import (
    AgentRequest,
    BusinessAgent,
    BusinessTool,
    RoleContext,
    RuntimeResult,
    ToolRegistry,
    business_tool,
)

class FakeRuntime:
    async def ainvoke(
        self, request: AgentRequest, tools: Sequence[BusinessTool]
    ) -> RuntimeResult:
        return RuntimeResult(output=f"echo:{request.input}", steps=[])

@business_tool(name="t", allowed_roles=["admin"])
def t() -> None:
    return None

agent = BusinessAgent(tool_registry=ToolRegistry([t]), runtime=FakeRuntime())
# await agent.ainvoke(AgentRequest(...))
```

参考仓库内测试：`tests/test_agent.py`。

## 12. 常见问题

**Q：安装后 `import business_agent` 失败？**  
确认安装的是本仓库产物；PyPI 名与导入名不同属正常，以 `python -c "import business_agent"` 验证。

**Q：模型调用报鉴权或网络错误？**  
检查 LangChain / 供应商所需环境变量与网络策略；异常会体现在 `TaskResult.status == failed` 的 `error` 字段。

**Q：模型总能「看到」不该调用的工具？**  
检查该工具的 `allowed_roles` / `required_permissions` 是否与当前 `RoleContext` 一致；检查是否用了另一份未同步的 `ToolRegistry`。

**Q：希望任务中途状态（running、waiting_tool）推送？**  
当前 `ainvoke` 以终态结果为主；更细粒度事件可参考 README「后续规划」或自行在自定义 `runtime` 中扩展。
